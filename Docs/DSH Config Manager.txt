# 角色

你是一名资深桌面应用、插件系统、TypeScript/JavaScript、配置迁移、数据安全与软件架构工程师。

你的任务是为 **DSH** 开发一个完整、可靠、可维护的 **配置备份 / 导出 / 导入 / 迁移插件**。

插件的核心目标是：

> 用户可以在一台 DSH 中一键导出自己的主要配置为一个 ZIP 文件，然后在另一台 DSH 中导入这个 ZIP，尽可能恢复原来的使用环境。

这不是简单地把整个配置目录复制成 ZIP。

需要设计一个真正的 **DSH Configuration Migration / Backup Manager**，需要考虑：

* 配置导出
* 配置导入
* 插件迁移
* Provider / Model 配置
* MCP 配置
* Prompt / Rules / Skills
* Workflow
* Workspace
* UI 偏好
* 环境变量
* Secret 安全
* 跨设备路径
* 操作系统差异
* DSH 版本差异
* 插件版本差异
* 配置冲突
* Dry Run
* 自动备份
* Rollback
* Schema Version
* Migration
* 数据完整性校验
* 错误恢复

# 第一原则：先研究 DSH，再写代码

在开始实现之前，必须先完整检查当前 DSH 项目的：

1. 插件 API
2. 插件目录结构
3. 插件 manifest 格式
4. 插件生命周期
5. 插件可以访问哪些 DSH API
6. DSH 配置存储位置
7. DSH 配置 Schema
8. Provider / Model 配置存储方式
9. MCP 配置存储方式
10. Plugin 配置存储方式
11. Prompt / Rules / Skills 存储方式
12. Workflow 存储方式
13. Workspace / Project 存储方式
14. UI Settings 存储方式
15. Secret / Credential 存储方式
16. DSH 是否提供官方导入导出 API
17. DSH 是否提供插件安装 API
18. DSH 是否提供配置读写 API

20. DSH 对插件权限的限制

**不要凭空假设任何 DSH API、目录、配置文件名称或者字段。**

如果项目代码中已经存在类似：

* backup
* import
* export
* settings
* migration
* config
* profile
* sync

等功能，优先复用现有实现。

如果某项能力 DSH 当前没有公开给插件，请明确指出：

> 当前 DSH Plugin API 无法直接完成 XXX。

然后设计安全合理的 fallback。

禁止为了让代码“看起来能运行”而编造不存在的 API。

  ui.json
  keybindings.json

ai/
  providers.json
  models.json

plugins/

  settings/

mcp/
  servers.json

  prompts/

  skills/
  commands/
  agents/

  workflows.json

  workspaces.json

实际结构必须根据 DSH 真实数据结构调整。

不要为了匹配这个示例而重复存储数据。

# 三、manifest.json

每个导出 ZIP 必须包含 manifest。

建议 Schema：

```json
{
  "schemaVersion": 1,
  "exporter": {
    "name": "DSH Config Manager",
    "version": "1.0.0"
  },
  "source": {
    "dshVersion": "unknown",
    "platform": "unknown",
    "arch": "unknown"
  },
  "exportedAt": "ISO-8601",
  "sections": {
    "settings": true,
    "plugins": true,
    "pluginSettings": true,
    "providers": true,
    "models": true,
    "mcp": true,
    "prompts": true,
    "rules": true,
    "skills": true,
    "commands": true,
    "workflows": true,
    "workspaces": true,
    "ui": true,
    "keybindings": true,
    "history": false,
    "secrets": false
  },
  "security": {
    "containsSecrets": false,
    "encrypted": false
  }
}
```

manifest 至少需要帮助程序判断：

* 谁创建了备份
* Export Schema Version
* 插件版本
* 来源 DSH Version
* 来源平台
* 创建时间
* 包含哪些 Section
* 是否包含 Secret
* 是否加密

# 四、Schema Version

这是非常重要的架构要求。

不要假设未来配置格式永远不会变化。

实现独立：

```text
schemaVersion
```

例如：

```text
v1
v2
v3
```

未来插件更新后，需要能够：

```text
Backup V1
↓
Migration
↓
Internal V2
↓
Current DSH Config
```

把迁移逻辑独立放置，例如：

```text
src/
  migrations/
    v1-to-v2
    v2-to-v3
```

不要把大量版本判断散落在 UI 和业务代码里。

# 五、Secrets 安全

这是最高优先级功能之一。

默认情况下禁止导出：

* API Keys
* Passwords
* Access Tokens
* Refresh Tokens
* OAuth Credentials
* Cookies
* Sessions
* Private Keys
* Authentication Headers
* Secret Environment Variables

普通 Export 应该：

> Export configuration WITHOUT secrets.

但是需要保留足够的信息，让导入后知道哪些 Secret 缺失。

例如：

```json
{
  "provider": "example",
  "apiKey": {
    "required": true,
    "exported": false
  }
}
```

导入完成后显示：

```text
3 credentials need attention.

OpenAI API Key
GitHub Token
Example MCP Token
```

用户可以重新填写。

---

# 六、敏感信息扫描

不能只根据固定字段判断 Secret。

导出之前实现 Sensitive Data Scanner。

检查疑似字段，例如：

```text
password
passwd
token
accessToken
refreshToken
apiKey
apikey
secret
credential
authorization
cookie
privateKey
clientSecret
```

大小写不敏感。

如果发现疑似敏感数据：

* 默认移除
* 标记
* 告知用户

不要把具体 Secret 内容显示在日志里。

---

# 七、Encrypted Full Backup

作为高级功能，可以允许用户：

> Include secrets

但是必须明显警告用户。

如果用户启用：

要求设置 Backup Password。

Secret 必须使用成熟、安全、经过验证的加密方案。

禁止：

* Base64 当加密
* 自己设计密码算法
* 明文 Secret
* 明文密码写进 ZIP
* 把解密密码写进 manifest

优先使用当前运行环境已经可靠支持的标准密码学方案。

如果无法安全实现，第一版宁可不支持 Secret 导出。

---

# 八、插件迁移

导出：

```text
Plugin ID
Plugin Name
Plugin Version
Enabled State
Plugin Configuration
```

优先不要把整个插件安装目录/二进制直接放入 ZIP。

导入时优先：

```text
读取 Plugin Manifest
↓
检查是否安装
↓
检查版本
↓
通过 DSH 官方插件机制安装/更新
↓
恢复 Plugin Settings
```

如果原版本已经不存在：

提供兼容版本或最新版本选项，并明确提示。

禁止偷偷安装不可信来源插件。

# 十一、冲突处理

支持至少：

### Merge

保留目标 DSH 原配置，并合并导入内容。

### Replace

导入配置覆盖相应目标配置。

### Skip Existing

已经存在的项目不修改。

对于具体冲突允许：

```text
Keep Current
Use Imported
Review
```

例如：

```text
Prompt "Coding Assistant"

Current:
modified 2026-08-10

Imported:
modified 2026-07-20

[Keep Current]
[Use Imported]
```

不要默认无脑覆盖用户数据。

# 十二、路径映射

必须处理跨设备绝对路径。

例如来源：

```text
/Users/alice/projects
```

目标机器不存在。

或者：

```text
C:\Users\Alice\Projects
```

导入到了 macOS/Linux。

Import Analyzer 必须识别：

* 不存在的路径
* OS 不兼容路径
* Workspace 路径
* MCP executable 路径
* Project 路径
* Script 路径

然后提供：

```text
Path Mapping

Old:
/Users/alice/projects

New:
[Choose Folder]
```

最好支持批量映射：

```text
/Users/alice/
→
/Users/bob/
```

所有相关路径自动替换。

# 十三、跨平台

考虑：

* macOS
* Windows
* Linux

不要默认路径分隔符都是 `/`。

注意：

* Path separator
* Home directory
* Executable extension
* Environment variables
* Shell
* File permission
* Symlink
* Case sensitivity

平台相关配置需要标记：

```text
portable
device-specific
platform-specific
```

默认优先迁移 portable 配置。

# 十四、环境变量

环境变量需要分为：

```text
Normal
Sensitive
```

例如：

```text
NODE_ENV=development
```

可以导出。

但：

```text
OPENAI_API_KEY=...
```

默认不能导出值。

可以只导出：

```json
{
  "name": "OPENAI_API_KEY",
  "required": true,
  "hasValue": false
}
```

导入后提醒用户填写。

# 十七、Rollback

如果导入过程中发生错误：

```text
Plugin installation failed
Invalid configuration
Write failed
Migration failed
Validation failed
```

尽可能恢复到导入之前。

UI 显示：

```text
Import failed.

Your previous configuration has been restored.
```

如果无法完整 Rollback：

必须明确告诉用户：

```text
Rollback partially completed.

These items may require manual recovery:
...
```

不能假装成功。

# 十八、配置完整性

导出时生成 checksum。

例如：

```text
integrity/checksums.json
```

对实际导出的文件计算 SHA-256 等成熟 hash。

Import 时：

先验证。

如果 ZIP 被损坏：

```text
Backup integrity check failed.
```

禁止继续自动导入，除非产品明确提供高级恢复模式。

---

# 十九、防止 ZIP 安全问题

Import ZIP 属于不可信输入。

必须防御：

* Zip Slip
* `../`
* Absolute Path
* Symlink Escape
* Malformed ZIP
* Zip Bomb
* 超大文件
* 超大解压后体积
* 大量文件攻击
* JSON 深度攻击
* 非预期 executable

所有文件只能解压到受控临时目录。

必须验证：

```text
resolvedPath.startsWith(allowedDirectory)
```

不要执行 ZIP 中携带的脚本或 executable。

# 三十一、重复导入

同一个 ZIP 导入两次不应该产生大量重复数据。

尽可能让操作具有 idempotency。

例如根据：

* Plugin ID
* Prompt ID
* Workflow ID

不要仅凭显示名称就武断覆盖。

# 三十二、删除策略

导入默认不要删除目标 DSH 中 ZIP 没有的东西。

例如：

目标有：

```text
Plugin A
Plugin B
Plugin C
```

ZIP 只有：

```text
Plugin A
Plugin B
```

默认 Import 后：

```text
A
B
C
```

而不是删除 C。

只有明确的：

```text
Mirror / Exact Restore
```

模式才能执行删除，而且必须给出强提示和 Snapshot。

# 三十四、禁止事项

绝对禁止：

1. 猜测 DSH API。

8. 用 ZIP 中路径直接写入文件系统。
9. 执行 ZIP 内脚本。
10. 导入失败却显示成功。

12. 无视现有项目 architecture。
13. 重复实现项目已有工具。
14. 修改与插件无关的大量代码。
15. 在没有必要的情况下引入大型 dependency。
16. 删除用户现有配置而不确认。
17. 因一个非关键项目失败而导致所有可恢复内容永久丢失。
18. 在 UI 中暴露 Secret。
19. 把设备 ID、Session、Cache 当作正常配置迁移。
20. 把整个 DSH data directory 当成“备份方案”。

# 最重要的产品原则

Do not log.

```text
Detect
Explain
Let the user decide
```
