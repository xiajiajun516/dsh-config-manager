## 3. 收录口径

**收进来**：一次性、有基线、有证据的横向分析（专项审计、竞品源码研究、技术方案对比）。必须写明审计基线（版本 + HEAD）与证据口径，结论要能按 `文件:行` 在同一基线上复核。

**不收进来**：

| 类型 | 该放哪 |
|---|---|
| 当前实现是什么样 | `docs/modules/` / `docs/components/` |
| 为什么当初这么设计（一次性取舍）| `docs/decisions/`（ADR）|
| 可复用的经验与证据 | `docs/lessons/<域>.md` |
| 已知债 / 硬限制 / 已知缺口 | `docs/maintenance/` |
| 对外契约 | `docs/spec/` |

## 4. 维护规则

1. **审计报告是快照，不做增量维护**：代码往前走之后，不要反复回来改旧报告的正常内容。发现结论已失效，在文首加一行 `> 失效说明（YYYY-MM-DD）：…，被 <新文档> 取代`，然后写新文档并在本索引登记。
2. **结论被采纳后要回迁**：报告里的「建议」一旦落地，正确的位置是 `docs/modules/`（当前实现）/ `docs/decisions/`（取舍）/ `docs/lessons/`（证据）；报告本身留着当历史依据。
3. **新增文档必须回本页表格加一行**，并跑 `node scripts/check-doc-paths.mjs`（0 命中）。
4. **不要在报告里记录真实凭据、token、私有主机名**：审计证据只写仓库相对路径与被脱敏的片段。
